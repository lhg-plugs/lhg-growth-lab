# lhg-gl-design：A/B 实验设计

> 目标：设计一个"结果可信"的实验——分组随机、样本够、周期对、停止规则事先定。
> 核心纪律：**样本量先算再开跑；停止规则写在看数据之前；分流异常先查再谈显著。**

## 1. 何时使用

- 假设已写好，要设计严谨的 A/B 实验 → 跑全流程
- 实验结果出来但两组流量对不上 → 查 SRM（第 6 节）
- 不确定实验要跑多久 → 用样本量折算天数（第 4 节）
- **不适用**：流量太小（算出来要跑 3 个月）→ 诚实降级：做前后对比 + 用户访谈，不要硬做 A/B

## 2. 输入与输出

### 输入
- 可证伪假设 + OEC + 护栏指标（来自 `lhg-gl-hypothesis`）
- 基线转化率、日/周流量
- 团队可接受的最长实验周期

### 输出
- 实验方案文档（含分组/随机化/样本量/周期/停止规则）
- `gl_audit.py` 校验通过（零 blocker）

## 3. 分步方法论

### 第 1 步：分组设计
- 默认 **50/50**：对照组（现状）vs 实验组（改动）。两组以上（如 A/B/C）也可以，但样本量要按组数涨，p 值要做多重比较校正。
- 写清每组是什么：对照组 = "蓝色按钮现状"，实验组 = "红色按钮"。**对照组不是"什么都不做"，而是"保持现状"**——现状本身可能也在变（如运营活动），要在方案里注明。
- 流量比例偏离 50/50 需要理由（如"怕新方案有 bug，先给 10%"）——可以，但样本量按最小组算，周期会变长。

### 第 2 步：随机化与分流一致性
- **分流单元**：按用户 ID 哈希分桶（不是按访问、不是按设备）。同一用户多次访问必须始终看到同一版本——今天看 A 明天看 B，数据就污染了。
- **登录态注意**：未登录用户用设备 ID/cookie 分桶，注明"同一人换设备可能串组"，这是已知局限，写进方案。
- **分流一致性检查（SRM）**：实验开始后先看两组样本量比例是否符合设计（如 50/50 设计，结果 55/45 且样本大 → 分流系统可能有问题）。判定前必查，命令见第 6 节。

### 第 3 步：样本量估算（必做）
```bash
python3 <插件目录>/scripts/audit/ab_stats.py samplesize --p1 <基线> --mde <相对提升> --format text
```
- **MDE（最小可检测效应）**：你"在乎"的最小提升，不是"期望"提升。问自己："提升 5% 值得全量吗？"不值得 → MDE 定 10%。
- 参数默认：显著性水平 0.05、功效 0.8——小白不用改，改了要写理由。
- **样本量不够的诚实处理**：算出来要跑 8 周 → 三个选择：① 提高 MDE（只测大变化）；② 降级为前后对比 + 访谈；③ 先涨流量。**不许**"先跑两周看看显著不显著"——那是 p-hacking。

### 第 4 步：周期与预热期
- 周期 = 2N / 日流量，向上取整；**不足 7 天按 7 天算**（消除星期效应：工作日和周末用户行为不一样）。
- **预热期**：前 2~3 天数据不纳入最终判定——应对新奇效应（用户对新变化的第一反应不代表长期效果）。
- 周期内**冻结其他大动作**：发版、改价、投放调整都会污染实验，排期时标出来。

### 第 5 步：停止规则（写在看数据之前）
```markdown
## 停止规则
- 跑满 <N> 天且两组样本量均达标后，用 ab_stats.py <ztest|ttest> 做双侧检验
- p<0.05 且提升幅度有业务价值 → 采纳；p≥0.05 → 放弃
- 中途不看显著性、不提前停止（护栏指标报警除外，见下）
- 护栏指标变差超过阈值 → 立刻停止并复盘，这是止损不是 p-hacking
```
**停止规则必须写在实验开始前**，写完锁死。开始后改规则 = 改裁判。

### 第 6 步：SRM（分流异常）检查
判定显著性之前，先验证分组本身没问题：
- 两组样本量比例 vs 设计比例：50/50 设计下，n=10000 时 52/48 以内的偏离多半是随机波动；偏离大（如 60/40）→ 查分流代码
- 检查项：新老用户比例、渠道分布在两组是否一致
- SRM 可疑 → **先修分流，再谈显著性**；分流坏了的实验，p 值再小也没意义

### 第 7 步：输出实验方案文档
```markdown
# 实验方案：<标题>（日期）
## 假设 / OEC / 护栏指标（来自 lhg-gl-hypothesis）
## 分组设计
## 随机化与分流单元
## 样本量（ab_stats.py samplesize 输出贴这里）
## 周期与预热期
## 停止规则
## 已知局限（如未登录用户串组）
```
跑 `gl_audit.py` 校验，blocker 清零再开跑。

### walkthrough：按钮颜色实验设计
假设：红色按钮购买转化率从 3.0% → 3.6%；日详情页 UV 20000。
1. 分组：对照组（蓝）50% / 实验组（红）50%
2. 随机化：用户 ID 哈希分桶
3. 样本量：`samplesize --p1 0.03 --mde 0.2` → 每组约 20000+ UV（按脚本实际输出）
4. 周期：2N/20000 向上取整，不足 7 天按 7 天；前 3 天预热期
5. 停止规则：跑满周期 + 样本达标 → ztest 双侧 → p<0.05 且提升有业务价值才采纳
6. 校验：`gl_audit.py` 跑一遍，blocker 清零

注意第 3 步的数字**以脚本实际输出为准**，不要心算——心算样本量是本 skill 禁止的。

### 多组实验（A/B/C）注意事项
- 每多 1 组，总样本量近似翻倍（每组都要攒够 N）
- 判定用 Bonferroni 校正：`ab_stats.py bonferroni --p "<pAB>,<pAC>"`
- 能只做 A/B 就不做 A/B/C：组数是成本，先验证"有没有用"，再验证"哪个最好"

### 开跑前最终检查（checklist）
- [ ] 假设文档已锁死（日期 ≤ 今天）
- [ ] 样本量脚本输出已贴进方案
- [ ] 停止规则已写进方案并告知相关人
- [ ] 分流代码已自测（测试账号进对组）
- [ ] 护栏指标报警阈值已定、报警通道已通
- [ ] 实验期间的大动作清单已确认无冲突
6 项全勾才能开跑——开跑按钮按下去之前，这是最后一道门。

> 一句话总结：好的实验设计是"开跑前把所有作弊的路都堵死"——样本量、周期、停止规则、分流检查，四堵墙缺一不可。

**设计文档的读者**：写方案时想象 3 个月后的自己在看——那时的你忘了所有上下文，文档要自包含：数字哪来的、为什么这么定、不确定的地方在哪。

## 4. 反模式

- ❌ 样本量不算直接开跑——大概率白跑两周
- ❌ 按访问分流——同一用户看两个版本，数据污染
- ❌ 周期 3 天——星期效应能把结论带偏
- ❌ 没有预热期——新奇效应的第一波数据最"好看"也最不可信
- ❌ 停止规则事后定——"p=0.06，再跑两天看看"是最贵的 p-hacking
- ❌ SRM 不查——分流坏了，显著性全是幻觉

## 5. 常见问题

- **Q：一定要 50/50 吗？10% 流量试错不行吗？** A：行，但样本量按最小组算——10% 组要攒够 N，周期是 50/50 的 5 倍。怕风险就用小流量，但要接受长周期。
- **Q：实验期间产品要发版怎么办？** A：评估发版是否影响实验页面/指标；影响 → 暂停实验或等发版后再开；不影响 → 写进"已知局限"。
- **Q：两组之外的用户（如内部员工）要排除吗？** A：要。测试账号、内部员工流量在分流前排除，写进口径。

## 6. 自检与反馈

开跑前自问：
1. 样本量算了吗？天数折算了吗？→ 没算不许开跑。
2. 停止规则写在看数据之前了吗？→ 写了才锁死。
3. SRM 检查项列了吗？→ 判定前必查。

标准冒烟用例：审计脚本 `GL-DSG-*` 校验设计完整性（见仓库根 `smoke_test.py`）。

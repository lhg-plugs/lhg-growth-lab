# lhg-gl-hypothesis：实验假设与 OEC

> 目标：让每个实验都有"可证伪"的假设和 1 个核心指标——假设写不对，后面的显著性检验全是白算。
> 核心纪律：**写不出"因为"就没有假设；核心指标只许 1 个。**

## 1. 何时使用

- 有实验想法，要把它变成严谨的 A/B 实验 → 跑全流程
- 实验做完了但说不清验证了什么 → 回来检查假设当初怎么写
- 团队每个人对"实验成功"理解不一样 → 用 OEC 对齐
- **不适用**：轻量增长实验（不需要显著性判定）→ 用兄弟插件 `lhg-user-growth`，更轻更快

## 2. 输入与输出

### 输入
- 实验想法一句话
- 产品背景（用户是谁、核心场景）
- 现有数据（基线指标，没有就写"无基线"）

### 输出
- 可证伪假设（"如果…那么…因为…"三要素齐全）
- OEC（1 个）+ 口径定义
- 护栏指标（最多 2 个）
- 观察指标清单（只看不判）

## 3. 分步方法论

### 第 1 步：写假设三要素
合格假设 = **改动** + **预期变化** + **原因**：
- ❌ "红色按钮更好" → ✅ "如果把购买按钮从蓝色改成红色，那么购买转化率会从 3.0% 提升到 3.6%，因为红色在当前页面视觉层级中更突出"
- ❌ "优化新手引导" → ✅ "如果把新手引导从 5 步压缩到 3 步，那么 7 日激活率会从 12% 提升到 16%，因为第 4~5 步的流失率最高"

三要素检查：
1. **改动**：具体到可执行（改哪、怎么改），"优化""提升体验"不算改动
2. **预期变化**：指标名 + 基线→目标数字；无基线写"无基线，先测 2 周"
3. **原因**：解释"为什么这个改动会影响这个指标"；写不出原因 → 假设是拍脑袋，打回

### 第 2 步：定 OEC（只 1 个）
OEC（Overall Evaluation Criterion）= 实验成败的唯一裁判。选题三问：
1. 假设里"那么"后面跟的指标是什么？→ 它就是 OEC
2. 它涨了，业务真的变好了吗？→ 不变好就换（如"点击率涨了但转化没涨" → OEC 该用转化率）
3. 它能在实验周期内测出来吗？→ 测不出来（如"年留存"）就降级用代理指标，并注明

**OEC 定了就锁死**：实验中途换 OEC = 换实验，之前的数据作废。

### 第 3 步：定护栏指标（最多 2 个）
护栏指标 = "不许变差"的指标。OEC 涨了但护栏掉了，实验照样算失败：
- 改转化流程 → 护栏：注册转化率 / 页面加载成功率
- 改推荐策略 → 护栏：用户投诉率 / 退订率
- 改价格展示 → 护栏：客单价 / 退款率

护栏指标也要有口径和"变差"的定义（如"下降超过 1 个百分点即报警"）。

### 第 4 步：列观察指标（只看不判）
观察指标 = 好奇但不做判定的指标（如停留时长、分享率）。规则：
- 观察指标**不参与**显著性判定，看了也不算数
- 写下来是为了防止"事后从观察指标里挑个显著的当成功"——清单在先，挑不出来
- 超过 5 个观察指标 → 砍，太多等于没重点

### 第 5 步：假设分级（可选，用于排期）
- **P0 验证假设**：决定产品方向的（如"用户愿意为这个功能付费"）→ 优先做
- **P1 优化假设**：改进现有指标的（如"红色按钮转化更高"）→ 按 ICE 排
- **P2 探索假设**：没把握的（如"加个社交功能会涨留存"）→ 先做最小验证，不直接上 A/B

## 4. 反模式

- ❌ 假设里没有数字——"会提升"不算预期变化，要"从 X 到 Y"
- ❌ 3 个 OEC——裁判多了，输了可以换裁判，等于没裁判
- ❌ 护栏指标缺失——OEC 涨了 5%、投诉涨了 50%，你还敢全量吗
- ❌ 观察指标事后转正——"点击率显著了，那就算成功吧"是最常见的 p-hacking 入口
- ❌ HARKing（先射箭再画靶）：看到数据后编一个"当初就是这么想"的假设——假设必须写在实验**开始前**，写进文档锁死

## 5. 假设模板（贴进实验方案）

```markdown
## 假设
如果<改动>，那么<指标>会从<基线>变为<目标>，因为<原因>。
## OEC
<指标名>（口径：<分子>/<分母>，<统计周期>），基线 <X>
## 护栏指标
1. <指标名>：变差定义 <……>
2. <指标名>：变差定义 <……>
## 观察指标（不参与判定）
- ……
```

## 6. 假设评审清单（写完逐项打勾）

- [ ] 改动具体可执行吗？（"优化"二字出现 → 打回）
- [ ] 预期变化有指标名 + 基线→目标数字吗？（无基线 → 写"无基线，先测 2 周"）
- [ ] "因为"部分是真因果吗？（"因为用户喜欢" → 套话，打回）
- [ ] OEC 只有 1 个吗？口径能算出来吗？
- [ ] 护栏指标有吗？（改动触及的上下游各想 1 个）
- [ ] 假设写在实验开始前了吗？（日期 ≤ 实验开始日期）

### walkthrough：从想法到假设
想法："详情页加个倒计时，能促进下单吧？"
1. 改动细化：在商品详情页价格下方加"优惠 X 小时后结束"倒计时（具体到位置与文案）
2. 预期变化：下单转化率从 2.5% → 3.0%（基线来自上周后台实测）
3. 原因：用户犹豫主因是"不急"，倒计时制造紧迫感
4. 成品假设："如果在详情页价格下方加优惠倒计时，那么下单转化率会从 2.5% 提升到 3.0%，因为用户犹豫主因是不急，倒计时能制造紧迫感。"
5. OEC：下单转化率（口径：下单用户/详情页 UV，按天）；护栏：退款率（阈值：上升超 0.5pp 即停）、客单价（阈值：下降超 5% 即停）

### 假设质量三档（自评用）
- **A 档（可直接开跑）**：三要素齐、OEC 口径可算、护栏齐、有基线
- **B 档（补一补再跑）**：缺基线或护栏阈值模糊——补上就升 A
- **C 档（打回重想）**：写不出"因为"、或"因为"部分是套话、或 OEC 不止 1 个
评审时先定档：C 档不许进入实验设计阶段。

> 一句话总结：假设是实验的"合同"——改动是甲方承诺，指标是验收标准，"因为"是履约逻辑。合同写模糊，验收必扯皮。

### 版本管理
假设文档每次修改记版本号（v1/v2…），修改原因写一句话。实验开始后的修改只许改错别字，不许改三要素——三要素变了就是新实验，另起文档。

## 7. 常见问题

- **Q：基线都不知道，假设里的数字怎么写？** A：写"无基线，目标待定"，先跑 1~2 周测基线再补；不许编基线。
- **Q：老板要求同时验证 3 个假设？** A：拆成 3 个实验排期；硬塞进 1 个实验里，哪个显著都说不清归因。
- **Q：假设被证伪了，文档要改吗？** A：不改历史记录。在复盘区写"证伪"，原假设留档——错假设是团队认知资产。
- **Q：假设的"因为"部分后来发现是错的，但实验显著了，算成立吗？** A：算"结果成立、原因存疑"——指标确实动了，但归因要重找。在复盘里写清，下次实验换"因为"再验证。
- **Q：OEC 和北极星指标是什么关系？** A：北极星是公司级长期方向（见 `lhg-user-growth` 的 `lhg-ug-metrics`），OEC 是单次实验的裁判；OEC 涨了，北极星不一定动——这是正常的，单次实验只对 OEC 负责。

## 7. 自检与反馈

写完假设自问：
1. 三要素齐了吗？→ 缺"因为"就打回。
2. OEC 只有 1 个吗？→ 多了就砍。
3. 假设写在实验开始前了吗？→ 跑完再补的叫 HARKing，不叫假设。

标准冒烟用例：审计脚本 `GL-DSG-001/002` 校验假设与指标（见仓库根 `smoke_test.py`）。

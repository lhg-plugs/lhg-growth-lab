# lhg-gl-antiphack：p-hacking 反模式

> 目标：识别并拦截实验中最常见的"自己骗自己"——p-hacking 不是恶意作弊，多半是无心之失，所以要用清单防。
> 核心纪律：**停止规则写在看数据之前；口径锁死；显著的指标事先定。**

## 1. 何时使用

- 实验设计评审 → 对照清单过一遍（`gl_audit.py` 自动查一部分）
- 实验进行中手痒想看数据 → 先读第 3 节
- 判定结果前 → 做一次反模式自查（第 6 节清单）
- 复盘时结论互相打架 → 查是不是有人 p-hacking 了
- **不适用**：轻量实验（不做显著性判定）→ p-hacking 概念不适用，用 `lhg-user-growth` 的复盘三态即可

## 2. 输入与输出

### 输入
- 实验方案（含假设、OEC、停止规则）
- 实验过程记录（什么时候看过数据、有没有改过什么）

### 输出
- 反模式检查结论：通过 / 发现 n 处（每处写清是什么、影响、怎么补救）

## 3. 分步方法论：六大反模式

### 反模式 1：提前停止（peeking）——最常见
- **长什么样**："每天看一下显著性，一看到 p<0.05 就停""跑了 5 天数据不错，提前结束吧"
- **为什么错**：反复看数据找显著，等于给了运气很多次机会；名义 5% 的假阳性率实际可能到 20%+
- **怎么防**：停止规则写在实验开始前（样本量 + 周期双达标才看）；实在忍不住看 → 只看**样本量进度**（跑了百分之几），不看 p 值
- **已经犯了**：诚实标注"提前停止，结果可能虚高"；结论降级为"探索性发现"，不许按"显著"全量

### 反模式 2：多重比较未校正——最隐蔽
- **长什么样**：同时看 5 个指标，挑 p 最小的报；"转化率不显著，但点击率显著了，也算成功吧"
- **为什么错**：看得越多，运气命中的概率越大
- **怎么防**：只定 1 个 OEC 做判定；非要多看 → `ab_stats.py bonferroni` 校正后再看
- **已经犯了**：把所有看过的指标全列出来，跑 Bonferroni 重算；校正后不显著 → 结论改"放弃"

### 反模式 3：HARKing（先射箭再画靶）
- **长什么样**：看到"红色按钮在女性用户中显著"后，补写假设"我们当初就是想验证女性用户"
- **为什么错**：数据里总能切出"显著"的子群，事后编假设等于拿运气当发现
- **怎么防**：假设写在实验开始前并锁死文档；子群分析只做**探索**，不下结论
- **已经犯了**：标注"事后探索性分析"，另起一个新实验验证，不许直接全量

### 反模式 4：换口径 / 换指标
- **长什么样**："7 日留存不显著，看看 30 日留存""转化率不行，换下单金额试试"
- **为什么错**：和多重比较一样，是给运气更多机会；且口径变了，前后不可比
- **怎么防**：OEC 与口径写进方案锁死；实验中不许换
- **已经犯了**：按原口径出结论；新口径的结果单列为"探索"，不许替代原结论

### 反模式 5：可选停止（optional stopping）变体
- **长什么样**："p=0.06，再跑两天看看""差一点显著，加点流量"
- **为什么错**：和 peeking 同源——"差一点"时继续跑，"显著了"就停，筛选机制保证了假阳性
- **怎么防**：停止规则里写死"样本量达标即停，不看 p 值决定是否继续"
- **已经犯了**：标注过程，结论降级；下次用序贯检验设计（允许中途看，但要用校正过的方法）

### 反模式 6：回归均值当增长
- **长什么样**：挑了个上周跌得最惨的渠道做实验，这周回升了 → "实验有效"
- **为什么错**：极端值自然会向均值回归，和实验无关
- **怎么防**：选实验对象时避开刚经历大涨/大跌的群/渠道；或设对照组——对照组也回升了，就是回归均值
- **已经犯了**：看对照组是否同步变化；同步 → 结论改为"无法归因"

## 4. 实验三阶段检查点

| 阶段 | 检查项 |
|---|---|
| 设计时 | 假设锁死了吗？OEC 只有 1 个吗？停止规则写了吗？样本量算了吗？ |
| 进行中 | 有没有看 p 值？有没有改口径/加指标？护栏报警了吗？ |
| 判定前 | 样本/周期达标了吗？SRM 正常吗？有没有事后挑指标？子群结论标探索了吗？ |

## 5. 补救原则

1. **诚实标注 > 掩盖**：犯了就写进报告，降级结论，不丢人；藏着掖着被发现才丢人
2. **降级不删除**：p-hacking 的实验数据不许按"显著"用，但可以当探索性发现，另起实验验证
3. **修流程不罚人**：p-hacking 多半是流程缺失（没写停止规则），补流程比追责有用

## 6. 自查清单（判定前逐项打勾）

- [ ] 停止规则是实验开始前写的吗？
- [ ] 实验中途看过 p 值吗？（看过 → 是否因此停过/延长过？）
- [ ] OEC 和口径和方案一致吗？
- [ ] 判定了几个指标？>1 → 校正了吗？
- [ ] 有没有事后加的子群结论？（有 → 标探索）
- [ ] 实验对象是不是刚大涨/大跌过？（对照组同步吗？）

## 7. 翻车案例（改编自常见真实场景）

**案例 A：每天看数据的运营同学**
某电商做首页改版实验，运营同学每天看一次显著性。第 4 天 p=0.03，大喜，提前全量。两周后大盘转化率反而掉了——第 4 天的"显著"是新奇效应 + peeking 的双重运气。
教训：停止规则写在开始前；想看就看样本量进度条。

**案例 B：5 个指标挑 1 个报**
某内容 App 测新推荐策略，同时看点击率、停留、分享、留存、付费 5 个指标。只有分享率 p=0.02，汇报写"实验显著"。Bonferroni 校正后 p=0.10，实际不显著。
教训：多指标要么只定 1 个 OEC，要么校正后再报。

**案例 C：事后编的"女性用户假设"**
某工具 App 全量实验不显著，分析师切出"25~30 岁女性"子群 p=0.01，补写假设"我们早就觉得女性用户更喜欢"。按子群全量后，大盘无变化。
教训：子群发现只能当探索，另起实验验证；HARKing 是拿运气当发现。

**案例 D：回归均值当增长**
某 SaaS 挑了上季度流失最严重的 3 个大客户做"挽回实验"，这季度 2 家续费了 → "挽回策略有效"。但对照组（没做挽回的同类客户）续费率也回升了——纯属回归均值。
教训：选实验对象避开刚大涨/大跌的群；必须有对照组。

### 给管理者的 3 句话
1. "实验期间不要问显著了吗"——问样本量进度，p 值跑满再看
2. "证伪的实验也是资产"——追责 p-hacking，不追责证伪
3. "停止规则要签字"——白纸黑字的规则，比口头"再看看"更能防手痒

> 一句话总结：p-hacking 的本质是"用灵活的流程去适配想要的结论"——解法只有一个：流程写在前面，锁死。

### 团队落地：把清单变成习惯
1. 实验方案模板里预置"停止规则"和"自查清单"章节（本插件命令已内置）
2. 每次判定前，评审人按第 6 节清单逐项问，答不上来不许下结论
3. 每季度复盘一次"差点 p-hacking"的案例，匿名分享——防的是下一次

**新人入职必读**：把本 skill 的"六大反模式"打印出来贴在工位。p-hacking 防的是无心之失——知道坑在哪，才不会掉进去。

## 8. 常见问题

- **Q：护栏报警提前停，算 p-hacking 吗？** A：不算。这是止损，且停的标准（护栏阈值）是事先定的。但主指标的结论要标"提前停止"，不许按正常显著用。
- **Q：老板天天问"显著了吗"，怎么办？** A：给他看样本量进度条（"跑了 60%"），不给 p 值。把"不提前看显著性"写进实验方案，老板签字——白纸黑字比口头承诺管用。
- **Q：序贯检验是不是就可以随便看了？** A：不是"随便"，是"用专门的方法看"。小白先用固定样本量设计；真有高频查看需求再研究序贯方法，本 skill 不展开。

## 8. 自检与反馈

用完本 skill 自问：
1. 六大反模式都对照过了吗？→ 跳过的那一项最可能就是坑。
2. 发现问题的，补救了吗（标注/降级/重算）？→ 发现不处理等于没查。
3. 流程补上了吗（停止规则模板进方案）？→ 只修这一次，下次还犯。

标准冒烟用例：审计脚本 `GL-PHK-*` 规则命中（见仓库根 `smoke_test.py`）。
